# Idempotency for Message Sending

This project uses an `Idempotency-Key` request header for message creation. The goal is to make retries safe without creating duplicate chat messages when a client times out, reconnects, double-submits, or does not receive the first response.

## API Contract

Clients must send a unique `Idempotency-Key` for each logical `POST /rooms/{room_id}/messages` operation.

```http
POST /rooms/{room_id}/messages
Authorization: Bearer <access_token>
Idempotency-Key: 8f4b1b7e-9e3a-4d8c-9c7f-123456789abc
Content-Type: application/json
```

```json
{
  "content": "Hola"
}
```

Recommended client behavior:

- Generate a new UUID or similarly high-entropy key for each new message send.
- Reuse the same key only when retrying the same logical request.
- Do not reuse a key for a different message body.
- Keep the key stable while a message is pending in optimistic UI state.

## Backend Guarantees

The backend treats `Idempotency-Key` as an opaque client-generated identifier. It does not trust the key by itself.

For each message send, the backend stores:

- `idempotency_key`: the received header value.
- `idempotency_request_hash`: a SHA-256 hash generated by the server from the normalized request scope and content.

The unique database constraint is:

```text
room_id + sender_id + idempotency_key
```

This scope prevents collisions between different users or rooms while still making repeated sends by the same user in the same room idempotent.

## Response Behavior

Expected behavior:

- New key + valid request: create and return the new message.
- Same key + same request hash: return the existing message.
- Same key + different request hash: return `409 Conflict`.
- Missing `Idempotency-Key`: FastAPI returns `422 Unprocessable Entity`.
- Invalid key format: return `400 Bad Request`.

The `409 Conflict` case is intentional. It prevents one idempotency key from being used to represent multiple different operations.

## Security Practices

Use the idempotency key only as a deduplication primitive. It is not an authorization mechanism and should never replace authentication, room membership checks, or rate limiting.

Current safeguards:

- Authentication is checked before creating messages.
- Active room membership is checked before creating messages.
- The idempotency key is scoped by authenticated user and room.
- The backend computes the request hash; the client does not provide it.
- The database unique constraint protects against concurrent duplicate inserts.
- `IntegrityError` is handled so racing retries can still return the existing message.
- Reusing the same key with different content returns `409 Conflict`.

## Relationship With Rate Limiting

Idempotency and rate limiting solve different problems:

- Idempotency protects legitimate retries from creating duplicate messages.
- Rate limiting protects the API from spam or abusive high-volume sends.

When rate limiting is added, the recommended order is:

```text
1. Authenticate user
2. Validate room exists
3. Validate active room membership
4. Validate Idempotency-Key
5. Check for an existing idempotent message
6. If the existing message matches, return it without consuming rate limit
7. If this is a new message, apply rate limit
8. Create message
```

This avoids punishing clients for retrying the same logical request.

## Duplicate Content With Different Keys

Idempotency cannot safely reject every duplicate message body. In chat, sending the same text twice can be intentional.

Example:

```text
Idempotency-Key: abc
content: Hola

Idempotency-Key: xyz
content: Hola
```

These are different logical operations. If the product needs protection against accidental double-clicks, use a short soft-deduplication window based on:

```text
sender_id + room_id + content_hash + short time window
```

Recommended window:

```text
1000-2000 ms
```

That soft dedupe should be separate from the hard idempotency guarantee because repeated identical messages may be valid user intent.

## Storage Notes

The current implementation stores idempotency metadata directly on `messages`, which is appropriate because message creation is the only idempotent operation currently supported.

If idempotency expands to many endpoints, consider a separate `idempotency_keys` table with:

- authenticated user scope
- operation scope
- idempotency key
- request hash
- response status
- response body or resource reference
- expiration timestamp

For multi-instance deployments, Redis can also be useful for short-lived locks, but the database constraint should remain the source of truth for persisted messages.
